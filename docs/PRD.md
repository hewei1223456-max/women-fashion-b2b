# 第一篇：产品总纲

## 一、产品定位

女装B2B行业的“认知基础设施 + 连接引擎 + 效率工具”。以七叔IP的行业认知为起点，将地标大店方法论、源头厂家货源、店主同频组局整合为一个多端平台。**不碰交易，收入驻费+功能费。**

## 二、三大核心模块

| 模块 | 回答的问题 | 目标用户 | 商业价值 |
|---|---|---|---|
| **资讯** | “我该怎么干？” | 店主 | 付费会员/游学卡 |
| **货源** | “我该找谁拿货？” | 厂家→店主、店主→厂家 | 厂家版本费 |
| **功能** | “我该怎么拍怎么写怎么剪？” | 店主+厂家团队 | 功能费/会员权益 |

三大模块互相导流，形成闭环：资讯→货源（看了方法论想找货）、货源→功能（找到款需要生成海报发朋友圈）、功能→资讯（用了工具发现内容不够好，回来学方法论）。

## 三、用户角色与权限

| 角色 | 认证要求 | 核心权限 | 付费等级 |
|---|---|---|---|
| 游客 | 无 | 浏览资讯摘要、厂家款列表（脱敏） | 免费 |
| 认证店主 | 营业执照 | 浏览全部资讯、发布内容、私信厂家、发起拼单、加入社群空间 | 精英/鲨鱼/游学 |
| 认证厂家 | 营业执照 | 发布款信息、发布内容、主动私信、查看加微数据、子账号管理 | 免费/基础/高级/企业 |
| 地标大店 | 营业执照+业绩审核 | 创建主页、发起活动、发布方法论 | 免费（平台邀请） |
| 内容讲师 | 资质审核 | 发布课程/文章/视频 | 平台签约 |
| 平台运营 | 后台账号 | 内容审核、用户管理、数据看板 | 内部 |

# 第三篇：三大核心模块详细设计

## 八、模块一：资讯板块

### 8.1 模块定位与呈现方式

**本质：解决“我该怎么干、别人怎么干的”。** 把大店的一切可公开的、可结构化的信息，变成店主能直接用的“行业情报”。同时，资讯板块是一个**内容社区**，用户不仅可以消费内容，还可以发布、编辑、删除、运营自己的内容，并与其他用户互动。

### 8.2 内容构成与呈现形式

| 内容类型 | 具体内容 | 呈现方式 | 权限层级 |
|---|---|---|---|
| 行业资讯早报 | 每日行业动态、批发市场政策、面料趋势、爆款风向 | 卡片流+每日推送 | 全体认证用户 |
| 游学蒸馏资料 | 每期游学的PPT、踩坑案例、现场问答 | 图文/PDF/视频+附件下载 | 对应游学期数成员 |
| 大店方法论 | 组货逻辑、陈列方法、搭配思路、定价策略 | 图文+视频+大店主页 | 精英群→基础，鲨鱼群→深度 |
| 组局方式 | 怎么组织拼单、怎么找同频店主、怎么和厂家谈条件 | 图文教程+案例 | 认证店主 |
| 找厂家攻略 | 十三行/南油/意法/濮院各市场拿货规则、筛选标准 | 图文+地图标注 | 认证店主 |
| 踩坑案例库 | 拿货被坑、组货失误、陈列无效的真实案例 | 图文+评论区讨论 | 精英群起步 |
| 讲师课程 | 组货、陈列、搭配、拍视频、做直播等专项技能 | 视频课程+图文笔记 | 部分免费+部分付费 |
| UGC内容 | 店主/大店/讲师/厂家发布的经验、心得、日常 | 图文/视频Feed流 | 公开/粉丝可见/群可见 |

### 8.5 推荐流排序逻辑（Phase 1规则引擎）

**第一层：风格匹配**——店主风格标签 × 内容风格标签，重合度越高排序越靠前。
**第二层：CES热度加权**——参考小红书CES评分体系，评论/提问权重35%，收藏28%，完读18%，分享12%，点赞7%。
**第三层：探索打散**——每10条内容中至少2条不同风格，防止内容同质化。

### 8.6 UGC内容发布与管理（资讯板块专属）

**发布功能：**
- 图文（1-18张图）、视频（最长5分钟）、长文（富文本）
- 标题（最长50字，支持#话题标签）
- 正文（最长5000字，支持emoji、@用户）
- 风格标签选择（必选1-3个）
- 关联款（可选，关联厂家款）
- 定位（可选，标注拿货市场）
- 权限设置（公开/仅粉丝可见/仅群成员可见）
- 草稿箱、定时发布

**内容管理：**
- 我的内容列表（按时间/浏览量/互动量排序）
- 编辑（发布后7天内可编辑，重新审核）
- 删除（软删除，30天内可恢复）
- 置顶（个人主页置顶3条）
- 内容数据看板（浏览量、点赞、收藏、评论、转发、加微数）
- 评论管理（查看/删除/置顶/回复）
- 私信管理（查看/自动回复/屏蔽）
- 内容申诉

**审核流程：**
```
用户发布 → 前端敏感词预校验 → 后端同步文本审核 → 
图片/视频异步审核（5-30分钟回调）→ 
通过→展示 / 不通过→人工复审→删除+警告/封禁
```

### 9.6 主动私信配额系统

店主端接收权重计算：

```
接收权重 = 近7日登录频次 × 0.4 + 近7日互动行为数 × 0.3 + 认证等级 × 0.3
```

不活跃的店主降低被私信优先级。配额计数用Redis实现，每日0点重置。

### 9.7 搜索排序权重

| 维度 | 权重 | 指标 |
|---|---|---|
| 基础信息完整度 | 25% | 款图质量、价格带、起订量、发货地 |
| 历史表现 | 35% | 款被浏览数、加微转化率、收藏数 |
| 反馈 | 25% | 有效加微反馈（客服回访确认） |
| 整体表现 | 15% | 是否认证、付费版本、违规记录 |

# 第四篇：UGC内容社区与互动体系（两板块通用）

## 十一、设计原则

**资讯板块和货源板块都是“内容社区 + 垂直功能”的融合体。**

参考模型：
- **小红书**：UGC图文/视频发布 + 点赞收藏评论 + 关注 + 个人主页 + 内容管理
- **抖音**：短视频发布 + 互动组件 + 私信 + 内容数据看板
- **Boss直聘**：双向私信 + 沟通记录

两个板块共享同一套UGC底层能力（发布、编辑、删除、互动、私信），但内容形态和审核规则不同。

# 第六篇：算法体系

## 二十、推荐算法分阶段方案

### Phase 1（上线即可用）：规则引擎

冷启动阶段没有用户行为数据，复杂模型效果不如规则。

**资讯推荐流排序：**
- 第一层：风格标签匹配（店主标签 × 内容标签，重合度排序）
- 第二层：CES热度加权（评论35% + 收藏28% + 完读18% + 分享12% + 点赞7%）
- 第三层：探索打散（每10条至少2条不同风格）

**货源推荐流排序：**
- 第一层：风格标签匹配 + 价格带匹配 + 拿货地匹配
- 第二层：加微转化率加权
- 第三层：随机打散（每10个款至少2个不同风格+1个不同发货地）

**冷启动新用户：**
- 前3次打开，每次混合推送3-5种不同风格款
- 第4次开始根据前3次行为收敛推荐
- 没有任何行为的新用户走“热门通道”——近7日加微转化率最高的款

### Phase 2（3-6个月数据积累后）：双塔召回 + Wide&Deep排序

**双塔召回模型：**
- User Tower：编码店主特征（风格标签、价格带、拿货地、历史浏览行为序列）
- Item Tower：编码款特征（风格标签、价格带、发货地、款图视觉特征）
- 计算点积作为匹配分，用ANN检索从海量款中快速筛选候选集
- 双塔模型的计算量小，用户塔和物品塔可以分别预计算，适合处理中等规模候选集

建模环节采用双塔向量检索完成高效候选生成，再以Wide&Deep进行精排输出Top-N，并配套冷启动处理与探索机制。

**Wide&Deep排序模型：**
- Wide部分负责“记忆”——店主已知偏好与款的关联（如“韩系店主喜欢韩系款”）
- Deep部分负责“泛化”——发现未曾出现的相关性（如“经常去南油的店主可能对新中式感兴趣”）
- 两部分融合计算最终排序分

**多目标优化：** 排序模型的目标函数以“加微转化”为核心，而非“浏览时长”。

### Phase 3（6-12个月）：行业大模型微调

当平台积累至少5000组高质量问答对后，用LoRA微调DeepSeek-7B/14B，部署到租用GPU服务器。行业相关问题走微调模型，通用问题走通用模型。

## 二十一、冷启动与探索机制

**探索-利用机制：** 新用户没有历史行为时，系统先提供相对多元的试探性内容，再根据用户的观看、停留、点赞、“不感兴趣”等反馈逐步修正判断。

**多模态兴趣探针（Phase 2）：** 用款图的视觉特征作为“探针”，在用户行为数据不足时，用视觉相似度做匹配。

**验证数据采集（合规设计）：** 图形选择/点选图像验证产生的数据可用于优化推荐系统，但后台只记录选择结果和动作类型，训练数据集做 K-匿名脱敏，设置页提供“数据用于推荐优化”的开关。

## 二十二、搜索排序算法

| 维度 | 权重 | 指标 |
|---|---|---|
| 基础信息完整度 | 25% | 款图质量、价格带、起订量、发货地 |
| 历史表现 | 35% | 款被浏览数、加微转化率、收藏数 |
| 反馈 | 25% | 有效加微反馈（客服回访确认） |
| 整体表现 | 15% | 是否认证、付费版本、违规记录 |

语义匹配搜索（Phase 2）：将款标题、风格标签、款图描述向量化，用向量检索做语义匹配。店主搜索“法式碎花”时，系统应能匹配到标题写“浪漫印花”但风格标签是“法式”的款。

# 第七篇：内容审核与安全

## 二十三、内容安全审核体系

### 23.1 审核范围
所有用户发布的文本、图片、音频、视频必须接入内容安全检测。

### 23.2 微信内容安全API
**文本审核：** 同步接口`msgSecCheck`，立即返回结果。
**图片/音频审核：** 异步接口`mediaCheckAsync`。

V2版本检测图片不会实时返回结果，需要等待5-30分钟后异步回调返回结果。需要提前在微信公众平台「开发」-「开发设置」-「消息推送」开启消息服务，检测结果在30分钟内推送到消息接收服务器。

V2版本必须传递微信小程序用户的openid，且用户需要在近两小时内访问过小程序。V2版本新增了scene参数，scene的取值不同，最终的检测结果也不同，需要传递合适的scene值。

### 23.3 审核流程
```
用户发布内容
  → 同步文本审核（立即返回）
  → 异步图片/视频审核（提交后等回调）
  → 审核通过 → 正常展示
  → 审核不通过 → 进入人工复审队列
  → 人工确认违规 → 删除+警告/封禁
```

### 23.4 消息接收服务器配置

| 步骤 | 操作 | 平台 |
|---|---|---|
| 1 | 登录微信公众平台 | mp.weixin.qq.com |
| 2 | 开发 → 开发设置 → 消息推送 | 后台 |
| 3 | 开启消息服务 | 后台 |
| 4 | 填写服务器地址和Token | 后台 |
| 5 | 验证Token | 后台 |

### 23.5 人工复审队列
审核不通过的内容进入人工复审队列。运营后台提供复审页面，支持：查看原文/原图、确认违规/误判、执行删除/警告/封禁操作。

### 23.6 多端审核适配

| 端 | 审核方案 |
|---|---|
| 微信小程序 | 微信内容安全API V2 |
| 抖音小程序 | 抖音内容安全API |
| 支付宝小程序 | 支付宝内容安全API |
| APP | 阿里云内容安全/腾讯云内容安全 |
| PC Web | 后端统一调用内容安全API |

# 第八篇：数据权限与合规

## 二十四、权限获取清单

所有权限申请必须绑定用户可感知的功能场景，遵循“最小必要”原则。处理个人信息应当具有明确、合理的目的，并应当与处理目的直接相关，采取对个人权益影响最小的方式。

| 权限 | 绑定场景 | 调用时机 | 合规要求 |
|---|---|---|---|
| 定位（粗略/单次） | 展示“附近的厂家/大店/订货会” | 用户进入该功能界面时调用一次 | 不申请后台持续定位 |
| 相册 | 上传营业执照、款图、店铺照片 | 用户主动点击“上传”时 | 使用系统存储访问框架，不索要完整相册权限 |
| 剪贴板 | 从抖音/小红书复制文案粘贴到内容工具 | 用户主动触发“粘贴”操作时 | 不后台静默读取 |
| 相机 | 拍照上传营业执照、款图 | 用户主动选择拍照功能时 | 停止使用后不得继续调用 |
| 设备信息（可变更ID） | 安全风控、统计分析 | 启动时 | 使用可变更标识符，不与不可变更硬件标识符关联 |
| 人脸识别 | 确认操作者是法人本人 | 认证提交时 | 验证完成后立即删除原始图像，不落盘、不训练、不共享 |

APP权限申请需遵循“最小必要”、“透明告知”、“主动同意”、“动态申请”、“敏感权限从严”等规则。

## 二十五、认证流程技术方案

### 25.1 营业执照OCR识别
接入第三方OCR服务（如CFCA安心验平台），一次扫描营业执照即可实现信息识别，包括注册号、法定代表人、公司名称、地址、营业期限、经营范围和主体类型。

### 25.2 人脸核身
基于人脸活体识别技术的身份认证方案，支持SDK、H5、小程序等多种方式集成。

### 25.3 认证流程
```
用户提交营业执照照片
  → OCR识别关键信息
  → 法人身份证正反面
  → 人脸核验（对接公安/CFCA接口）
  → 对公账户打款验证（0.01-0.1元）
  → 审核通过 → 获得“认证店主/认证厂家”标识
```

### 25.4 数据合规底线
- 个性化推荐关闭入口是强制性的，向用户提供便捷的关闭选项
- 不得因用户拒绝非必要权限而拒绝提供核心服务
- 权限申请必须是动态的、场景化的，不能在启动时一揽子申请
- 用户同意需满足“知情、自愿、明确”，不得默认勾选

## 二十七、支付方案

选择微信支付**普通服务商模式**。普通服务商自身无法作为普通商户直接发起交易，必须传入特约商户商户号的参数信息。

### 27.1 分账场景

| 场景 | 分账规则 | 接收方 |
|---|---|---|

- 分账申请审核周期约7个工作日
